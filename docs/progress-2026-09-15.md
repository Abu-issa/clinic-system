## Implemented

Infrastructure uses Identity 10.0.11 via the central package file. `ClinicDbContext` now derives
from IdentityDbContext while preserving the medical mappings and IUnitOfWork behavior. Identity
accounts have independent IDs, explicit doctor association, persisted enabled state, and a
single expiring challenge. UserManager/RoleManager handle passwords, grants, authenticator keys,
verification, recovery-code generation/redemption and security-stamp updates.

The only full application cookie remains ClinicStaff. ClinicStaffIntermediate carries no roles,
permissions or MFA claim and is never used by medical endpoint authorization. Enrollment and
second-factor completion require a password-verified five-minute persisted challenge. Successful
verification consumes it under a SQL application lock and issues a 30-minute full session with
amr=mfa and persisted grants. Both schemes check revocation on every authenticated request.

POST login, enrollment setup/verification, TOTP, recovery, logout and revocation validate CSRF.
GET csrf issues real antiforgery request tokens for anonymous, intermediate and full identities.
Successful identity transitions return refreshed request tokens. All auth responses are no-store,
including authorization failures. Cookies are Secure/HttpOnly/SameSite Strict; no remembered-device
or browser storage token path exists. Five failures trigger 15-minute Identity lockout. The auth
routes share a bounded fixed-window rate limiter. Logout revokes all account sessions.

The explicit local command provisions only the first responsible Doctor with existing Doctor IDs
and scopes, and is safe to rerun without resetting credentials or grants. Local administrative
operations support disable, revoke, password reset, MFA reset and full grant replacement; each
invalidates sessions and challenges. No HTTP registration, staff CRUD, patient OTP, Flutter or MVC UI.
Appointment and schedule application services were not changed. Clinic-wide booking remains
Doctor/Receptionist + MFA; scoped operations retain their existing policies.

password respectively. Setup instructions now state the 12–1024-character range. No migration or
appointment-service change was needed.

password/MFA reset and stamp changes. Clearing a browser cookie alone leaves copied cookies usable;
these logout/revocation endpoints additionally change persisted security stamps, invalidating copies

## Focused pre-commit review — Patient Medical Record Foundation

This section supersedes the earlier complete-snapshot removal semantics and 232-test checkpoint.

Confirmed findings and targeted fixes:
1. High integrity risk: a current-version empty/partial clinical snapshot superseded unseen and
   verified rows by omission. Reproduced before fixing. Every active ID must now be retained or
   explicitly listed in SupersededEntryIds; implicit omission returns 400 without saving. Duplicate,
   foreign, inactive and retained-and-removed IDs are rejected. PUT remains a complete snapshot;
   a future partial/lazy client must not treat it as PATCH.
2. High integrity risk: missing nullable clinical JSON properties were silently treated as null,
   demonstrated by clearing a recorded blood type. Clinical basic/entry value fields now require
   explicit JSON presence. Optional values can still be intentionally null; missing fields return 400.
3. High access risk: removing a persisted patient scope without rotating the stamp left an issued
   cookie authorized. The real Identity regression reproduced 200 after removal. Patient-record
   scope/permission claims and roles are now rechecked against persisted records on every full
   request carrying these grants. Removed grants invalidate the full cookie; added grants require
   login. Supported set-grants still rotates stamps and clears challenges.
4. High privacy risk: EF SaveChangesFailed diagnostics included the duplicate MRN in SQL exception
   text even with sensitive-data logging disabled. Reproduced using concurrent HTTP creation and
   an ILogger sink capturing both formatted state and exception text. The API suppresses
   SaveChangesFailed/CommandError diagnostics. Controlled conflicts remain sanitized 409 responses;
   unexpected failures retain the sanitized exception-type/trace-ID API handler.
5. Medium unit-of-work risk: cancelled/unexpected saves left Added entities tracked, and a later
   SaveChanges inserted the rejected patient. Both regressions reproduced before fixing.
   PatientRecordsStore now discards pending record state on all save exceptions before rethrowing.
   Existing validation/concurrency cleanup remains.
6. During verification of the stricter snapshot contract, re-querying a fully loaded tracked
   aggregate could merge new database children into its old parent/version, returning an incorrect
   400 instead of the existing test's expected SQL concurrency 409. The store now reuses a fully
   loaded aggregate within its unit of work. The original SQL rollback assertion remains passing.
