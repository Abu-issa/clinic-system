## Implemented

Infrastructure uses Identity 10.0.11 via the central package file. `ClinicDbContext` now derives
from IdentityDbContext while preserving the medical mappings and IUnitOfWork behavior. Identity
accounts have independent IDs, explicit doctor association, persisted enabled state, and a
single expiring challenge. UserManager/RoleManager handle passwords, grants, authenticator keys,
verification, recovery-code generation/redemption and security-stamp updates.

The only full application cookie remains ClinicStaff. ClinicStaffIntermediate carries no roles,
permissions or MFA claim and is never used by medical endpoint authorization. Enrollment and
second-factor completion require a password-verified five-minute persisted challenge. Successful
verification consumes it under a SQL application lock and issues a 30-minute full session with
amr=mfa and persisted grants. Both schemes check revocation on every authenticated request.

POST login, enrollment setup/verification, TOTP, recovery, logout and revocation validate CSRF.
GET csrf issues real antiforgery request tokens for anonymous, intermediate and full identities.
Successful identity transitions return refreshed request tokens. All auth responses are no-store,
including authorization failures. Cookies are Secure/HttpOnly/SameSite Strict; no remembered-device
or browser storage token path exists. Five failures trigger 15-minute Identity lockout. The auth
routes share a bounded fixed-window rate limiter. Logout revokes all account sessions.

The explicit local command provisions only the first responsible Doctor with existing Doctor IDs
and scopes, and is safe to rerun without resetting credentials or grants. Local administrative
operations support disable, revoke, password reset, MFA reset and full grant replacement; each
invalidates sessions and challenges. No HTTP registration, staff CRUD, patient OTP, Flutter or MVC UI.
Appointment and schedule application services were not changed. Clinic-wide booking remains
Doctor/Receptionist + MFA; scoped operations retain their existing policies.

## Completed focused pre-commit review

The interrupted review added `AdministrativePasswordsMustFitTheLoginContract`, a two-case
theory covering initial provisioning and administrative password reset. Neither case had a
reported result when that turn stopped. On resumption, both failed: Identity accepted passwords
longer than the HTTP login's 1024-character limit, so operators could create an unusable account
or reset an existing account to an unusable password (P2 correctness defect).

Minimal fix: register an additional Identity password validator in `StaffIdentityRegistration.cs`
that rejects lengths above 1024, while retaining Identity's existing password validators/hashers.
Both regressions now pass and verify failure leaves no provisioned account or preserves the old
password respectively. Setup instructions now state the 12–1024-character range. No migration or
appointment-service change was needed.

Added focused real-HTTP tests for cookie-scheme substitution, repeated setup with untrusted
identity/key input, and concurrent TOTP/recovery completion using independent clients holding the
same challenge. They pass: substitution fails, setup preserves the stored key, and only one request
issues a full cookie. Existing captured-cookie tests pass after logout, revoke-sessions, disable,
password/MFA reset and stamp changes. Clearing a browser cookie alone leaves copied cookies usable;
these logout/revocation endpoints additionally change persisted security stamps, invalidating copies
on their next request. Requests already authorized before revocation may still finish.
