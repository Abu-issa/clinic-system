## Configurable development assumptions

These defaults are provisional workflow assumptions, **not clinician-approved production settings**.
Configuration is the `BookingPolicy` section in API appsettings (normal environment overrides supported).
Settings are validated at startup; the Application layer owns validation and immutable policy logic, while ASP.NET options wiring stays in API. No new dependencies or policy administration API/UI.

| Setting | Default | Accepted range |
|---|---:|---:|
| ConsultationMinutes | 30 | 1–1440 |
| FollowUpMinutes | 15 | 1–1440 |
| SlotStartIntervalMinutes | 15 | 1–1440 |
| MinimumAdvanceNoticeMinutes | 60 | 0–525600 |
| BookingHorizonDays | 30 | 0–366 |

The bounds prevent invalid durations, non-advancing slot loops and unbounded policy windows. A valid combination can legitimately produce no slots (for example, notice longer than the horizon).
Configuration is captured once by the policy singleton; restart the API to apply policy changes consistently. Existing appointments are never rewritten, moved or cancelled when configuration changes.

### Boundary semantics

- Clinic timezone remains `Asia/Amman`, resolved using `TimeZoneInfo`; no fixed Amman UTC offset.
- Horizon is based on the **start's local calendar date**: today through today + 30, both included. It is not a rolling 720-hour interval.
- Minimum notice is elapsed time: start >= now + 60 minutes, including equality. Starts must also be strictly in the future (even if configured notice is zero).
- Slot grid starts at each active period's own local start and advances by the configured interval. Sub-interval/second/tick offsets are rejected. Durations need not be multiples of the interval.
- The entire appointment must fit within one period; ending exactly at the period end is allowed. It may not bridge a gap or cross local midnight, matching the current working-period model.
- Overlap is `existing.start < candidate.end && existing.end > candidate.start`, allowing adjacency. Overlapping/duplicate periods do not produce duplicate slots.
- Ambiguous or invalid local **start or end** times are explicitly skipped in generation and rejected in mutations; the server never chooses an offset for an ambiguous time. Duration is elapsed UTC time. A transition strictly inside an interval is permitted if endpoints are valid/unambiguous and the whole interval fits the local period.
- DateOnly minimum/maximum values are unsupported; malformed date/type input is 400. Out-of-horizon dates return 400. Closed/no-period days and days with no remaining notice-compliant slots return 200 with an empty list. Missing doctors return 404, inactive doctors 409.
- Availability uses a bounded UTC envelope around the local day covering every legal timezone offset, avoiding ambiguous-midnight resolution just to fetch blocking intervals.

## API contracts

### Staff availability

`GET /api/staff/doctors/{doctorId}/availability?date=YYYY-MM-DD&appointmentType=Consultation`

Supports `Consultation` and `FollowUp` (case-insensitive query names). Requires authenticated Doctor/Receptionist, MFA, `permission=appointments.availability`, and matching `appointment_doctor_id`. No CSRF for GET; responses use no-store.

Response: `localDate`, `timeZoneId`, `appointmentType`, `durationMinutes`, and `slots` containing only `startsAtUtc`/`endsAtUtc`.
Availability is advisory, not a reservation. It is not a transactionally frozen snapshot; concurrent changes can invalidate it immediately.

### Booking contract change

`POST /api/staff/appointments` now takes `patientId`, `doctorId`, `startsAt`, `appointmentType`.
The old end-time argument/property has been removed. An obsolete extra JSON `endsAt` is ignored and cannot override server duration. Undefined or omitted appointment types are rejected. JSON accepts named types and defined numeric enum values (1/2); examples use names.
Existing staff authorization and CSRF requirements are unchanged. Success remains 201 with `appointmentId`.

### Rescheduling

- Existing GET details now also include `appointmentType` (null for legacy).
- `GET /api/staff/doctors/{doctorId}/appointments/{appointmentId}/rescheduling/availability?date=YYYY-MM-DD` resolves stored duration/type and excludes only the appointment selected by this authorized, doctor-scoped resource. It requires existing `appointments.reschedule` permission and scope, with no arbitrary exclusion query parameter. No type/duration input.
- Rescheduling availability can include the unchanged current time; a no-op POST continues returning `appointment_time_unchanged`. It is a free-slot view, not a list of guaranteed valid mutations.
- POST retains `startsAt`, `endsAt`, `reason`, `expectedRowVersion` for compatibility. End-start must equal the stored duration exactly; otherwise 400 `duration_changed`. No type changes.
- Row versions remain Base64. Stale versions/save-time conflicts remain 409 `appointment_changed`; success returns `changeId` and the updated `rowVersion`.
- Common policy failures use Problem Details with `code` and `traceId`: `off_grid`, `insufficient_notice`, `outside_booking_window`, `invalid_local_time`. Availability conflicts remain 409 `time_slot_unavailable`/`outside_working_hours` for mutations.

OpenAPI endpoint descriptions and `Clinic.Api.http` examples were updated. Dates/IDs/cookies in examples are placeholders, not seeded production records.

## Legacy strategy and deployment

Existing rows remain null (explicitly legacy/unclassified). No historical duration is inferred from type and no historical times change. A migration upgrade test verifies a 47-minute legacy appointment keeps both times and null type.

Rescheduling preserves stored duration, type (including null), identity, doctor and status; changed configuration only affects new bookings and slot generation for new bookings.
