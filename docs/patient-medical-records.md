# Patient medical record foundation

This slice adds administrative patient records and relational clinical history, without a patient
login account. It does not implement visits, prescriptions, tests, storage, patient OTP or a UI.

## Model and migration

Migration: 20260915105237_AddPatientMedicalRecordFoundation. Generated by EF Core, not hand-created.
The upgrade adds nullable MRN, legacy paper number, opaque cover reference and emergency-contact
columns to Patients, plus a SQL rowversion. Existing IDs, names, phones, dates, Appointment.PatientId
foreign keys and appointment rowversions are preserved. Existing MRNs remain NULL. There is no
backfill, patient/clinical seed, table recreation or profile creation during migration.

MRNs supplied by the new workflow are trimmed, required and at most 32 characters. The SQL unique
index filters on MedicalRecordNumber IS NOT NULL; comparison follows the database collation.
Legacy NULL MRNs coexist. Phone numbers are not unique. LegacyPaperFileNumber is separate from MRN.
The optional cover reference is metadata only: do not dereference it as an arbitrary URL or claim
that the referenced document has been uploaded/authorized. No storage integration exists.

PatientMedicalProfiles has a unique PatientId and a separate rowversion. Five independent relational
entry tables store allergies, chronic conditions, medication names/status, surgeries and family
history. There is no JSON medical blob or prescribing model. All new medical FKs use Restrict.
No deletion endpoint exists. Downgrading drops the new clinical tables and columns and loses their
data; it is not an operational rollback plan. Back up before a separately approved local upgrade.
This implementation task does not apply the migration to ClinicDb.

## Access matrix

Every endpoint requires the existing full persisted staff session and MFA. Permissions are explicit.
Every existing-patient route additionally requires an exact persisted patient_record_id scope;
doctor association and appointment/schedule scopes do not imply patient-record access.
On every full-session request carrying patient-record grants, the cookie validator also compares
those scope/permission claims and roles with current persisted grants. Removal invalidates the
entire old session even if a claim editor did not rotate the stamp. Grant additions require a new
login. The supported administrative path remains set-grants, which rotates stamps as before.

| Operation | Roles | Permission |
|---|---|---|
| Create patient | Doctor, Receptionist | patients.admin.write |
| Read administrative details | Doctor, Receptionist | patients.admin.read |
| Update administrative details | Doctor, Receptionist | patients.admin.write |
| Read clinical profile | Doctor, DoctorAssistant | patients.clinical.read |
| Save/review/supersede clinical profile | Doctor | patients.clinical.write |

Reception has no clinical access, even with a clinical permission. Assistants have read-only clinical
access; no final review or editing authority is introduced. There is no automatic scope grant when
a patient is created. The creator receives the creation result; an operator must explicitly authorize
subsequent access. Unknown/out-of-scope patient IDs return 403 before lookup; an authorized missing
resource returns 404. Entry IDs are resolved only inside the selected patient's loaded profile.
There is no client-supplied profile ID or staff attribution. Role/permission/scope headers have no effect.

The four new permission names are allowed by the existing local set-grants operation but are NOT
added to first-account provisioning or existing accounts. Example (manual CMD, no credentials):

    dotnet run --no-build --no-launch-profile --project backend/Clinic/src/Clinic.Api -- staff set-grants --user-id STAFF_ID --roles Doctor --permissions patients.admin.read,patients.admin.write,patients.clinical.read,patients.clinical.write --scopes DOCTOR_ID --patient-scopes PATIENT_ID --environment Development

Use actual existing IDs, never names. This replaces the complete grants, rotates the security stamp,
and clears pending authentication. Omitted --patient-scopes means no patient scopes; include all
intended patient scopes on every replacement. Existing --scopes still requires at least one Doctor ID.
No real grants are changed by this task. Initial onboarding remains the first-doctor-only command.
Existing Doctor/Receptionist + MFA clinic-wide booking policy is unchanged.

## API contracts

All responses under /api/staff/patients use Cache-Control: no-store, including errors.
Every POST/PUT requires the antiforgery cookie and X-CSRF-TOKEN from /api/staff/auth/csrf.
Use HTTPS, cookie-aware clients, no saved credential/body collections, and no browser localStorage.
Request bodies are limited to 128 KiB and each clinical category to 100 input entries.
DTOs explicitly project fields; domain entities and staff/security identifiers are not serialized.
Enums use their numeric values in these endpoints (see MedicalRecordEnums.cs).
byte[] RowVersion values use JSON Base64, matching existing concurrency conventions.

| Method/route | Contract |
|---|---|
| POST /api/staff/patients | CreatePatientRequest: name, phone, DOB, required MRN, optional legacy references and emergency contact; 201 administrative details |
| GET /api/staff/patients/{patientId} | Administrative details only, including RowVersion |
| PUT /api/staff/patients/{patientId} | UpdatePatientRequest: name, phone, DOB, emergency contact, ExpectedRowVersion; 200 updated details |
| GET /api/staff/patients/{patientId}/medical-profile | Current active entries and basics; no persisted profile returns Unknown with empty version and MinValue update timestamp |
| PUT /api/staff/patients/{patientId}/medical-profile | SaveMedicalProfileRequest: complete snapshot of basics and all five entry lists, ExpectedRowVersion, optional SupersededEntryIds; 200 new snapshot |

MRN and legacy references are not changed by the administrative PUT; legacy assignment/correction
requires a later approved workflow. Future DOB and incomplete emergency contacts are rejected.
A POST example with entirely synthetic values:

    {"fullName":"Synthetic Example","phoneNumber":"synthetic-shared","dateOfBirth":null,"medicalRecordNumber":"SYN-EXAMPLE","legacyPaperFileNumber":"PAPER-EXAMPLE","legacyCoverImageReference":null,"emergencyContactName":null,"emergencyContactPhone":null,"emergencyContactRelation":null}

First profile save, explicitly recording no known allergies:

    {"bloodType":null,"allergyStatus":1,"smokingStatus":null,"diabetesType":null,"allergies":[],"chronicConditions":[],"medications":[],"surgeries":[],"familyHistory":[],"expectedRowVersion":null}

Unknown is 0; NoKnownAllergies is 1; HasKnownAllergies is 2. Active allergies require 2.
All basic fields, all five lists and expectedRowVersion must be present in JSON, even when explicitly
null/empty. Clinical entry value/source/review fields must also be present (including nullable reaction,
severity, notes and performedOn); Id can be omitted for a new entry. Missing fields return 400 rather
than clearing recorded values. Subsequent saves must use the latest 8-byte version.
Missing/stale versions never authorize blind replacement; stale updates and competing first saves
return 409. SQL save transactions roll back child inserts/supersessions if aggregate concurrency fails.

**Clinical PUT is complete replacement of the active snapshot.** Include each retained entry's ID.
Every active ID must appear either in its retained entry list or in the explicit supersededEntryIds
array. Omission alone is rejected with 400; it cannot remove unseen or verified entries. An ID cannot
be both retained and explicitly removed. SupersededEntryIds defaults to an empty list, is limited to
500 IDs, and rejects duplicates, foreign-profile IDs and inactive IDs. Changed content supersedes the prior row and adds
a new row; history remains in SQL. Unknown, foreign-profile, duplicate and inactive IDs are rejected.
The current GET returns active entries only; no separate history browser is implemented.

Source 1 is staff, 2 is patient-reported. ReviewStatus 1 is pending, 2 verified.
Only doctors can submit this command. Patient source means the doctor records patient-reported
information, not a patient login or self-service endpoint. Pending reports can be explicitly verified
without losing their original source/recorder. Verified entries cannot be downgraded, and changed
patient-sourced content cannot replace an identified verified entry. Staff-sourced entries are
doctor-attested and persist verification identity/time. Doctor-directed removal requires explicit supersededEntryIds, not patient-authorized deletion. A future patient/assistant write path must use a separate
append-only pending-report command; this doctor command must never be exposed to it.

Error responses follow Problem Details (code and traceId): invalid_csrf_token/invalid input 400,
authentication 401, authorization 403, patient_not_found 404, patient_changed/profile_changed/
medical_record_number_already_exists 409. Unknown JSON fields do not mutate entities or grants.

## Operational limits and pending clinic decisions

Clinical read access, administrative reads and changes do not yet have a dedicated durable access
audit trail. Entry provenance/supersession and last profile updater are persisted, but are not a complete
legal medical-record audit or historical basics ledger. Establish retention, read-access auditing,
backup encryption/recovery, restricted SQL access and incident procedures before real clinical use.
Do not enable HTTP body logging, EF sensitive-data logging or proxy/APM payload capture.
The API suppresses EF SaveChangesFailed and CommandError diagnostics because SQL exception text can
include an MRN even without sensitive-data logging. Expected uniqueness conflicts return sanitized
409 responses. Unexpected API failures retain the sanitized exception-type/trace-ID handler.

The patient-ID scope list is carried in protected cookies and is suitable only for a small explicitly
assigned pilot set; large patient panels need server-side resource grants rather than growing cookies.
Administrative creation is deliberately clinic-wide with an explicit permission; read access is scoped.
Clinic decisions remain: MRN numbering/case convention and legacy assignment, patient allocation and
grant administration at clinic scale, assistant editing workflow (currently absent), correction/reason
and audit requirements, clinical-history presentation, and future authorized document storage.
